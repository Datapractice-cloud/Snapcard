### The bug underneath the bug

The admin cutoff was computed **on the server**:

```js
const since = new Date();
since.setHours(0, 0, 0, 0);   // Hostinger's midnight, probably UTC
```

For an IST admin that starts the day at 05:30 local, so the early morning's leads fell
off a day early. `/leads` never had this because its `startOf()` runs in the browser.
Moving the filter client-side fixed the timezone as a side effect — no offset passed to
the server, no URL params, no round trip per pill. That is the whole reason this approach
was chosen over plumbing a timezone through.

**A scare worth recording:** three consecutive queries returned 9, then 8, then 7 leads.
Not a bug — the user was deleting test leads through the app while the queries ran. A
single script running `countDocuments()` and `listRecentLeadsFromAtlas()` together
returned 7 and 7. Check atomically before believing a count has drifted.
