## Session 4 — Salesforce writes a real Lead, end to end

### What was done

**Salesforce works.** Against `thinkvibessoftware3-dev-ed`, two upserts with one
`clientId` returned the same `leadId` (`00QQy00000nmzY2MAI`), all 16 mapped fields
landed verbatim, `LeadSource = Event`, and the card image attached as a ContentVersion
(1 file linked). The user confirmed the Lead in the Salesforce UI. `0 of 15 blocked`,
Lead fields visible 27 -> 42.

Getting there took fixing two separate things — one in the org, one in our code.

### Problem 1 — the org: grants in a permission set that can never hold them

The field permissions were configured in `Snapcard Integration`, assigned to the
integration user, and had **no effect**. Three rounds of checking before the cause was
visible:

- Assigning the permission set changed nothing (`11 of 15` before and after).
- Not propagation — a re-run minutes later was identical.
- SOQL agreed with describe (`No such column 'Email' on entity 'Lead'`), so it was not
  a metadata-caching artifact.
- The writable-field list was the tell: `LastName, FirstName, Salutation, Company,
  Status, OwnerId, IsConverted, IsUnreadByOwner, SnapCard_Client_Id__c` — every one of
  those is required or system, which FLS **cannot** hide. So zero grants were landing,
  not some.
- Cause: `Snapcard Integration`'s Object Settings list has **no `Lead` row at all** —
  nor Account, Contact, Opportunity or Case. It was created under a license that
  excludes the CRM objects, so Lead permissions can never be added to it.
- Fix: the grants went into `Integration Permission Set`, which already carried the
  Lead object access all along.

**My own misstep:** I twice told the user to tick field permissions on a page that has
no such row, instead of reading "Lead is absent from Object Settings" as a licensing
constraint. The user had to paste the whole object list before it was visible.

### Problem 2 — our code: the upsert key was in the request body

With FLS fixed, the first real write still failed, both times:

```
INVALID_FIELD: The SnapCard_Client_Id__c field should not be specified
in the sobject data
```

`mapFields()` emitted the external id into the PATCH body while the URL already keyed
on it. Salesforce refuses that combination, so **every lead would have come back
`needs_review` at the event** — a 100% failure, not an edge case.

It survived because Salesforce has been off since the code was written, and the unit
test asserted the id **was** in the body: the suite confirmed the bug rather than
catching it. Fixed in `4afc396`, assertion inverted into a regression test, reason in a
comment. `npm test` 164 passed, typecheck and lint clean.

Note `PLAN-1` Task 5 specifies `mapFields` as producing `SnapCard_Client_Id__c`. That
instruction is wrong and must not be followed back in.

### What is still open

- **The test Lead `00QQy00000nmzY2MAI` could not be deleted** —
  `INSUFFICIENT_ACCESS_OR_READONLY`. The integration user has no Delete on Lead. Harmless
  for production (the app never deletes), but `npm run sf:smoke` will fail its cleanup

- **`IP Relaxation = Enforce IP restrictions`** on the External Client App. Calls

  production write will fail auth until it is trusted. Not yet addressed.
- `SALESFORCE_ENABLED` is still `false` everywhere — it was set only inside one-off
