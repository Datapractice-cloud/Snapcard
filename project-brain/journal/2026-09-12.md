## Session 3 — Salesforce diagnosed; it is one permission set away

### What was done

Measured the real state of the Salesforce org with read-only probes instead of
trusting the brain's recorded diagnosis — which turned out to be half wrong.

- **`checkLeadFieldAccess()`** (a describe, no writes) against the live org:
  `SnapCard_Client_Id__c` **ok**, `FirstName` / `LastName` / `Company` ok, and
  11 blocked: `Title`, `Email`, `Phone`, `Website`, `Street`, `City`, `State`,
  `PostalCode`, `Country`, `Description`, `LeadSource`.
- **Identity probe:** running as `integration.user@thinkvibes.com`, in a
  **Developer Edition** org (`…develop.my.salesforce.com`), not a sandbox.
- **Object-level describe:** `Lead createable=true updateable=true`,
  `ContentVersion createable=true`, `ContentDocumentLink createable=true`,
  API `v60.0` reachable.
- Established with the user: this DE org **is** the production target, they are a
  System Administrator on it, and the goal is event-ready rather than a local proof.

### Corrections to what the brain recorded

- **`SnapCard_Client_Id__c` is NOT missing.** The brain (inherited from `context.md`)
  said the org lacked it. It exists and is writable — someone created it since that was
  written. The upsert key, the hard prerequisite, is in place.
- **The FLS half was exactly right:** 11 standard Lead fields hidden from the
  integration user, matching the count recorded.
- **Auth was never broken.** The client-credentials flow, the Connected App, the
  Run As user and the secrets all work. That layer was never the blocker and the brain
  never said otherwise — but nobody had confirmed it either.

### Problems hit & how fixed

- **A hypothesis I raised and then disproved.** The integration user's license is
  `Analytics Cloud Integration User`, while the `Minimum Access - API Only
  Integrations` profile is conventionally paired with the `Salesforce Integration`
  license. I flagged it as a likely blocker. An object-level describe settled it:
  `Lead.createable=true`, `ContentVersion.createable=true`. The license restricts
  nothing that matters here. Recorded because the mismatch looks alarming and will
  look alarming again to the next person who notices it.
- **The first guidance I gave was bigger than necessary.** I wrote a click-path
  creating a new permission set with Lead object CRUD. The object describe then showed
  CRUD is *already* granted, so something already gives this user object access and the
  edit needed is field permissions only — likely on an existing permission set.
  Revised before the user acted on it.
- **`npm run sf:smoke` cannot prove anything while `SALESFORCE_ENABLED=false`** —
  `upsertLead` short-circuits to `{ status: "skipped" }`, so the run past the field
  check is meaningless. The field check itself is not gated, which is why it was called
  directly rather than through the script.
- **Temp probe scripts** were written into `scripts/` (tsconfig paths resolve `@/`
  there) and deleted immediately after. The working tree was left clean. A permanent
  read-only `npm run sf:check` would be worth having before the event — not built yet.

### Files touched

None. Every probe was read-only and the scratch scripts were removed.
